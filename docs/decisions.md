# 決策紀錄

技術取捨的原因，供日後查詢。新的在上面。

## 2026-10-22　設定頁分類、緩慢的擴充功能逐一調整

**決定**（使用者要求）：
- 設定頁先列出分類（每個分類下方以小字列出它的項目，不必點進去就知道在哪），點了才列出該分類的設定；標題列「‹ 分類」或 Esc 回上一層。
  不用左側分類欄＋右側內容：面板只有 420 px 寬，兩欄都太擠。分類就是 `Pref::group`，新增設定不必另外維護分類表；
  「命令列」從「外觀」分出來。
- 緩慢的擴充功能可逐一決定是否照樣放在第一層：`hide_slow`（原 `show_slow`，反過來）為總開關，`allow_slow` 列出照樣顯示的 CLSID
  （CLSID 不隨語言、版本改變；同一擴充功能的檔案／資料夾／背景合併成一列）。總開關關閉時全部照樣顯示，表格以灰階表示、不能切換，
  但保留各列的選擇，重新開啟時恢復。`show_slow` 只存在一天，沒有轉換舊設定。
- 表格只列出目前判定為緩慢的（記錄 7 天後失效）；被允許的仍會計時，變快後記錄失效就從表格消失。

## 2026-10-22　兩層右鍵選單、自動隱藏緩慢的擴充功能

**參考**：Windows 11 檔案總管把舊的選單放到「顯示更多選項」（微軟的說明：IContextMenu 二十年沒有規範地膨脹、在檔案總管的程序內執行，
影響效能與穩定）；Directory Opus 可逐一封鎖擴充功能、偵測到不穩定會自動封鎖，另有「隱藏 Windows 項目」；Files 4.2.7 也改善了選單速度
（找不到實作細節）。這台電腦量到的瓶頸是 Windows 自己的動詞（見下一則），第三方擴充功能載入後大多不到 15 ms，但 WinRAR 對檔案每次約 70 ms。

**決定**（使用者選定）：
- 預設兩層：第一層自繪（立即出現、跟著主題），「顯示更多選項」／Shift+右鍵開完整的 Windows 選單；設定可改回直接顯示完整選單。
  「此電腦」與樹狀列仍直接用完整選單（第一層的命令都以清單的選取為對象）。
- 第一層也放第三方擴充功能（只取 DLL 不在 Windows 資料夾的；Windows 自己的項目由程式的命令代替，或在「顯示更多選項」中）。
  由 ShellHost 在預先準備時自行建立、計時、讀出項目；還沒準備好就不放，避免選單顯示後才變長而點錯。
- 自動隱藏緩慢的：同一程序中第二次起連續兩次超過 50 ms，或第一次（含載入 DLL）超過 1 秒；依檔案、資料夾、背景分開判斷；
  記錄 7 天後失效重新量。隱藏的列在選單最下面（灰字）。設定可照樣顯示（見上一則的逐一調整）。

**限制**：完整的 Windows 選單無法拿掉單一擴充功能（沒有 API，除非自己重寫整個 Shell 選單），所以「隱藏」只作用在第一層。
自繪的項目沒有文字（owner-drawn）無法顯示、項目沒有圖示；擴充功能的子選單在準備時就展開讀出（送 WM_INITMENUPOPUP）。

## 2026-10-21　右鍵選單預先準備

**量測**（不顯示選單，`ctx_menu_timing` 測試，release）：時間幾乎都在 `QueryContextMenu`。第一次 2.9 秒（載入擴充功能），
之後文字檔約 205 ms、圖片 140 ms、三個檔案 115 ms、背景 65 ms、資料夾 46 ms。逐一量第三方擴充功能（7-Zip、WinRAR、PowerToys…）
載入後每個都不到 10 ms；改用 CMF_DEFAULTONLY 降到 3–11 ms、CMF_NOVERBS 不到 2 ms，所以時間在 Windows 自己的動詞
（開啟、編輯、開啟檔案、Windows 11 的應用程式動詞），不能省略。

**決定**：事件觸發的預先準備。游標在清單停住 150 ms（與預覽相同）送 `ShellJob::Prepare`，主機建好選單；按右鍵時若項目、資料夾相同、
剪貼簿序號（`GetClipboardSequenceNumber`，不開啟剪貼簿）沒變、沒按 Shift、未滿 60 秒就直接顯示，否則照舊當場建立。
選單關閉後佇列空了再為同樣的項目準備一份。同一批佇列中被後面的選單工作取代的 Prepare 不執行。

**取捨**：游標移動時主機會在背景做這些工作（每停住一列約 50–200 ms CPU，在 ShellHost 執行緒，不影響 UI）；
複製、貼上等剪貼簿工作若剛好排在準備之後會晚一點完成。第一次準備可能要數秒，所以 PREPARING 超過 10 秒才算卡住（一般工作 3 秒）。
鍵盤的選單鍵沒有預先準備（焦點改變不送 Prepare），先看滑鼠的效果。

## 2026-10-19　右鍵選單的自訂項目、主題欄位的說明

**決定**：
- 右鍵選單只加系統選單沒有的項目：選取多個項目時的「批次重新命名」（另有在新分頁開啟、我的最愛、設定縮圖）。
  「複製路徑」「在終端機開啟」不加：Windows 11 的選單已經有「複製為路徑」與「在終端機中開啟」，再加會出現兩個同名的項目。

  要在每個繪製處登記區域，成本高；先看提示是否足夠。
- 範例腳本 rename_pattern.lua 的單元測試把 `%LOCALAPPDATA%` 換成測試資料夾（之前會寫到使用者真正的資料夾）；復原記錄刪不掉時改為清空，
  沒有記錄時一律回報「沒有可以復原」（推測偶發的測試失敗是記錄檔被短暫鎖住而沒刪掉，未能重現；修改後連跑 15 次都通過）。

## 2026-10-17　命令列、下拉選單、提示；快速鍵編輯器改成面板

**決定**：
- 命令面板視為工程師專用；一般人用的入口是工具列下方的命令列（Windows 11 檔案總管的樣式，使用者選定）：
  新增▾、剪下、複製、貼上、重新命名、刪除、排序▾、檢視▾、⋯。所有內建命令都能從命令列或「⋯」的分組子選單找到（測試檢查每個選單項目都有名稱）。
- 不能用的按鈕變灰色而不隱藏（位置固定才記得住）；判斷「有沒有選取」用選取數，與檔案總管相同（只有焦點時剪下、複製是灰色的，
  雖然快速鍵仍會作用在焦點項目上）。
- 提示：停留 500 ms 出現，已有提示時移到另一個按鈕立即切換；內容是名稱、快速鍵與不能用的原因。選單的快速鍵靠右顯示。
  提示與選單都用 D2D 自己畫，跟著主題（Win32 tooltip 與選單不跟主題，深色模式下會不一致）。
- 視窗變窄：先收起文字，再把右邊的按鈕移進「⋯」，「⋯」永遠留著。
- 自訂：在按鈕上按右鍵（移除、左右移）、在「⋯」項目上按右鍵（加到命令列）、完整的「自訂命令列」面板（拖曳、↑↓、改名稱、
  Fluent 圖示或自己的圖片檔、加入腳本命令、進階的自訂命令腳本）。結果存在程式旁的 `toolbar.toml`；沒有這個檔案時用預設，
  再加上 config.toml 舊的 `[[button]]` 中命令列與選單沒有的命令（預設的「新資料夾」「終端機」已在「新增▾」「⋯」裡，不重複）。
  預設設定檔不再有 `[[button]]`。
- 快速鍵編輯器改成右側面板：一個命令可以有多個按鍵（＋ 加上、× 移除），被其他命令使用時先詢問取代或取消（原本是直接搶走），
  可依名稱或依按鍵搜尋。命令面板中的舊快速鍵模式移除。
- 新命令：`file.newfile`（新增文字文件）、`cmdbar.edit`、`cmdbar.hide`；`view.sort --asc|--desc` 不給 `--by` 時維持目前的欄位。

**原因**：
- 命令列而不是傳統選單列或只有「⋯」：使用者選了 Windows 11 式；常用操作一眼可見，最符合現代 Windows 的習慣。多佔一列高度，
  所以可在設定頁隱藏（`command_bar.visible`）或只顯示圖示（`command_bar.labels`）。
- `toolbar.toml` 另存而不寫進 config.toml：按鈕清單是陣列表，逐行修改不可行（與 keys.toml 相同的理由）。
- 衝突時詢問而不是直接取代：不寫程式的人不知道按鍵原本做什麼，默默搶走會讓原本的功能「壞掉」。
- 執行檔 3.85 → 4.09 MB（+6%，超過退步容差）：命令列、選單、提示、兩個面板與約 80 條翻譯；離 10 MB 門檻很遠，
  啟動時間、記憶體、幀時間沒有退步，所以只把基準的 `exe_mb` 更新為 4.09（其他指標維持原本的基準）。

## 2026-10-17　主題編輯面板改成不寫程式也會用

**決定**：
- 原則：介面要符合現代慣例，同時讓不會寫程式的人不必知道色碼、數值範圍或設定檔寫法。
- 顏色：點一下展開 16 個色票（含強調色與常見灰階），另有「更多顏色…」（系統選色對話框）與直接輸入色碼。
- 數字：滑桿＋−／＋＋滾輪；選項：下拉選單（取代點一下輪替）；開關：切換鈕；字型：系統安裝的字型清單（第一次展開才在背景列舉）。
- 風格與深淺色可以在面板上換（`Theme::rebased`）：保留已改的欄位；換深淺色時不沿用背景、文字等配色（深色的背景放到淺色上會看不清楚），
  只保留強調色與資料夾顏色。
- 檔案顏色規則可在面板新增（依類別：圖片、影片、音樂、文件、壓縮檔、執行檔、程式碼，或自訂樣式）、改色、刪除。
- 改過的欄位顯示 ↺ 還原；標題顯示「尚未儲存」。「儲存」在內建主題上詢問名稱另存（原本是灰色不能按，使用者不知道要改用「另存新主題」）。
- 工具列最右側固定一個齒輪按鈕開啟設定頁，不受設定檔的按鈕影響：不會用命令面板的人也找得到設定。

**原因**：
- 即時套用到整個畫面就是最直接的預覽，不另外畫縮小的預覽圖（重複一份繪製程式碼，也不如實際畫面準確）。
- 不自己畫 HSV 選色器：色票涵蓋大部分需求，系統對話框處理其他情況，程式碼與維護成本低很多。

## 2026-10-17　設定頁

**決定**：
- 設定頁（`settings.open`，`Ctrl+,`）停靠在窗格右側，與主題編輯面板同一個位置（兩者只開一個）；選項點一下展開、開關點一下切換、
  文字點一下輸入；快速鍵、主題、設定檔等複雜的設定以列出的命令開啟各自的編輯器。
- 修改立即套用，並在背景寫回 config.toml：只改那一行的值（`zing_core::prefs::write_pref`），保留其餘內容與註解，
  沒有這一行就插入在同一節，沒有這一節就加在最後；改完重新解析，讀回來不是新的值就不寫入並提示用文字編輯器修改。
- `Ctrl+,` 從「以記事本開啟 config.toml」改成開啟設定頁（與 VS Code 等程式的習慣相同）；設定頁底部與命令面板仍可開啟設定檔。

**原因**：
- 寫回 config.toml 而不像快速鍵另存檔案：這些是單一的值，另存一份會讓「config.toml 寫的值沒有效果」難以理解；
  逐行替換不需要 toml_edit 相依（執行檔大小），也不會打亂使用者的註解。快速鍵是陣列表（`[[key]]`），逐行修改不可行，所以維持 `keys.toml`。
- 停靠面板而不是另開視窗：修改時能直接看到效果（主題、樹狀列位置），也沿用主題編輯器已有的繪製與點擊處理。
- 不做工具列按鈕、縮圖產生器的表單：它們是陣列表、內容是命令腳本，文字編輯器比表單好用。

## 2026-10-17　i18n（繁中、英文、日文）與快速鍵編輯器

**i18n 的決定**：
- 原文（繁體中文）就是鍵，翻譯放在 `crates/zing-core/i18n/{en,ja}.toml`，build.rs 編譯成依原文排序的靜態表，查詢時二分搜尋。
- `tr!("…{名稱}…", 名稱 = 值)`：參數以名稱代入，翻譯可以調整語序；不支援 `{:.1}` 等格式，先格式化成字串。
- 測試掃描原始碼中所有 `tr!`／`tr_key!`／`tr(` 的原文，檢查每個翻譯檔都有、沒有多餘的、參數名稱一致。
- 語言由設定檔 `language` 決定（預設 `auto` 跟隨 Windows 的顯示語言；簡體中文也用繁體）；DirectWrite 的語系跟著換
  （日文 ja-JP；英文用 Windows 的地區設定，中文檔名仍用使用者習慣的字形）。
- Lua API 文件與 LuaLS 定義檔由同一份翻譯產生；README 另有英文、日文版；預設設定檔有英文、日文範本（只差註解與按鈕名稱，測試檢查解析結果相同）。

**原因**：
- 原文當鍵：程式碼照樣看得懂，不必另外維護一套鍵名；改了原文，測試會指出翻譯要跟著改。缺點是原文的小修改（標點）
  也要同步翻譯檔，但這正是需要檢查翻譯的時候。
- 靜態表而不是啟動時解析 TOML：繁中不需要任何查詢，其他語言也不必在第一幀前解析檔案（啟動門檻 150 ms）；
  代價是執行檔大小：3.69 → 3.85 MB（約 560 筆 × 2 種語言，含執行時產生 zing.d.lua 用的 Lua API 說明），效能基準的 exe_mb 因此更新為 3.85。
- 不用 fluent、gettext 等函式庫：需要的只有查表與具名參數，函式庫會增加相依與執行檔大小。
- 隔離模式固定繁中：冒煙測試比對許多畫面文字，效能測試的結果也要可重現；英文、日文另有冒煙測試步驟檢查與截圖。
- 不翻譯記錄檔（zing-index 的 index.log 等）：給開發者看，翻譯了反而難以搜尋原始碼。

**快速鍵編輯器的決定**：沿用命令面板（`Palette::keys`）：篩選、`Enter` 錄製、`Ctrl+Delete` 移除、`Ctrl+R` 還原預設；
結果寫在程式旁的 `keys.toml`，只含與「預設＋config.toml」不同的按鍵（`cmd = ""` 表示解除），載入順序在 config.toml 之後。

**原因**：
- 另存 `keys.toml` 而不改寫 `config.toml`：使用者的設定檔有註解與自己的排列，程式改寫 TOML 會弄亂（要保留註解得加 toml_edit 相依）；
  編輯器擁有自己的檔案，想手動改的人仍可在 config.toml 寫 `[[key]]`。
- 錄製取代命令原本的按鍵、搶走已被使用的按鍵並告知：與 VS Code 等編輯器相同，最少步驟；「還原預設」不會把已被其他命令使用的按鍵搶回來。
- `Esc` 用來取消錄製，所以不能指定成快速鍵。

## 2026-10-17　小項目：檔案作業速度、我的最愛排序、窄窗格欄位、命令面板 middle、{ask:}、手動縮圖

**檔案作業的速度（MB/s）**：複製開始時另一條執行緒計算來源的總大小（資料夾先問索引服務，否則逐資料夾加總；
同一磁碟區的移動只是改名，不計算），速度 =「進度 × 總大小」在最近 3 秒的變化。不在複製前先掃描：大量檔案時
掃描本身要數秒，作業不該因此晚開始；總大小算出來之前只顯示百分比。Shell 的 `UpdateProgress` 單位不是位元組，
所以不直接拿來換算。

**我的最愛的順序**：另存在 `session.toml` 的 `favorite_order`（含設定檔中的項目），不改寫設定檔，也不把設定檔的
項目複製進 `favorites`（否則從設定檔移除後仍會留著）。移動時原地重排樹狀列的節點，不重建：重建會再展開到目前的
資料夾並把焦點移過去，連按 `Ctrl+↑` 就會失效。

**窄窗格的欄位**：整欄收起（類型 → 大小 → 修改日期），不再依比例縮小。縮小後日期、大小被截斷反而看不出內容；
類型可從圖示與副檔名看出，最先收起。

**命令面板 `position = "middle"`**：新增選項而不改 `center` 的行為。`center` 的輸入框固定不動（打字時不跳），
`middle` 整個面板永遠置中，結果數改變時移動輸入框（子視窗，`window::move_edit`）。

**命令變數 `{ask:提示}`**：解析時遇到沒回答的提示就先顯示輸入框（沿用 Lua `ask()` 的面板），回答後以答案重新解析
整個腳本；同一個提示只問一次，`Esc` 取消整個腳本。不在背景等待（UI 執行緒不能阻塞），也不佔用工作池的執行緒。

**手動指定縮圖**：圖片複製到 `%LOCALAPPDATA%\zing-explore\custom-thumbs`，檔名是「磁碟區序號-NTFS 檔案 ID」。
以檔案 ID 為鍵，改名、在同一磁碟區內移動後仍有效；ID 只在這台電腦有意義，所以不放在程式旁（與其他設定不同）。
複製圖片而不是記住路徑：原圖移動或刪除後縮圖仍在。沒有任何手動縮圖時不開檔取得 ID，不影響一般縮圖的速度。

## 2026-10-16　搜尋面板的排序按鍵、自然排序

**決定**：
- `Ctrl+1`–`Ctrl+5`（名稱、路徑、副檔名、大小、日期）改寫輸入框中的 `sort:`（`namequery::set_sort`），同一個鍵再按一次反向，
  `Ctrl+0` 移除；不另外保存排序狀態。
- 服務端的名稱、路徑、副檔名排序改用自然排序（`namequery::natural_cmp`，逐位元組比較已轉成小寫的 UTF-8，連續數字以數值比較），
  規則與資料夾清單的 `text::natural_cmp` 相同；服務版號 4（快照格式不變）。

**原因**：
- 排序只存在查詢字串裡：按鍵的結果看得到、可以再編輯，命令與 Lua 組出的查詢也一樣，不會有「面板狀態」與「查詢字串」兩個來源互相矛盾。
- 用數字鍵而不是點欄位標題：搜尋面板沒有欄位標題，焦點一直在輸入框，手不必離開鍵盤。

## 2026-10-16　全磁碟搜尋的路徑比對、篩選、排序與不分大小寫

**決定**：
- 語法在 `zing_core::namequery`：含 `\` 的詞比對完整路徑，`ext:`、`size:`、`dm:`、`file:`、`folder:` 篩選，`!` 排除，
  `sort:` 排序；整個查詢字串送給服務解讀，zing 端只先檢查有沒有無法解讀的詞（有就提示、不送出）。
- 索引多存每筆記錄的修改時間（`$STANDARD_INFORMATION`，Unix 秒 u32），快照第 3 版、服務版號 3。
- 排序在服務端：先比對完所有磁碟，只用 heap 保留排序在前的 `2 × limit` 個候選，再依序以呼叫者身分檢查權限。
- 不分大小寫：Unicode 小寫對應（`char::to_lowercase`）。只有查詢含「有大小寫之分的非 ASCII 字母」時，
  名稱才轉成小寫；否則沿用逐位元組比對（ASCII 字母轉小寫）。
- 路徑比對：每個資料夾的路徑只轉小寫並比對一次（快取），每筆記錄只檢查跨越資料夾與名稱的部分。

**原因**：
- 語法沿用 Everything 的寫法（`ext:`、`size:`、`dm:`、`\` 比對路徑），習慣的人不必重學；放在查詢字串裡，
  不必為每個篩選增加協定欄位或介面元件，Lua 與命令也能直接組出查詢。
- 修改時間每筆 4 位元組：E: 約 300 萬筆多 12 MB（索引約 +6%）。日期篩選與排序很常用，值得；u32 秒到 2106 年，
  1970 年以前視為不知道。資料夾的修改時間只在它自己的記錄有變更日誌事件時更新：子項目的新增、刪除只產生
  子項目的事件，要正確必須每次重讀上層資料夾，成本不值得。
- 排序只保留前 `2 × limit` 個：`ext:jpg sort:size` 可能有數十萬個符合，全部保存（服務以 LocalSystem 執行）會暫時
  多用數十 MB；多保留一倍是給權限過濾的餘裕，不夠時顯示「還有更多」。
- 大小寫：中日韓文字沒有大小寫，ASCII 查詢遇到的非 ASCII 字元轉小寫後也不會變成 ASCII（K、İ 等極少數例外），
  所以這些情況不必轉換名稱。100 萬筆的基準：子字串 12.8 → 16.8 ms、萬用字元 6.6 → 9.2 ms、中文 12.4 → 16.8 ms
  （多了篩選與修改時間的判斷）；含 é 的查詢約 17.6 ms。
- 路徑：逐筆組完整路徑再比對，100 萬筆要 1 秒；資料夾先比對、每筆只看「資料夾路徑最後 (長度 − 1) 個位元組 + 名稱」
  後約 120 ms（只有路徑條件的最壞情況，有名稱條件時先以名稱過濾）。

## 2026-10-16　索引服務有自己的版號，zing 啟動時自動更新舊版

**決定**：`indexproto::SERVICE_VERSION` 是服務自己的整數版號（與 zing 的版本無關），服務回答 `version` 請求；
不認得這個請求的服務視為版號 1。zing 在第一幀之後於背景詢問一次（每個程序一次），已安裝的服務較舊時直接以 UAC
執行程式旁的 `zing-index --install`，UAC 視窗就是使用者的確認；沒有安裝服務時不做任何事。

**原因**：
- 服務以 LocalSystem 執行、安裝在 Program Files，zing 更新後不會跟著更新；新功能（例如全磁碟搜尋）需要新的協定，
  舊服務只會回「無法解析請求」，使用者很難知道要重新執行「啟用 NTFS 索引服務」。
- 用獨立的整數版號而不是比對執行檔內容或 zing 的版本：開發時每次建置執行檔都不同，比對內容會一直要求更新；
  只有服務真的改變時才加 1，使用者只在需要時看到 UAC。代價是修改服務時要記得加 1（寫在 CLAUDE.md）。
- 不先顯示自己的確認對話方塊：UAC 本身就要確認，多一層只是多按一次。取消時不記住，下次啟動再詢問，
  避免使用者一次取消後就永遠停在舊版。
- 只升級不降級：服務比 zing 新（執行較舊的 zing）時不動它。

## 2026-10-15　全磁碟搜尋：索引服務保存所有檔名，結果以呼叫者身分過濾

**決定**：NTFS 索引服務除了資料夾，也保存每筆 MFT 記錄的名稱（UTF-8 連續存放，快照第 2 版），提供 `search` 查詢；
zing 以命令面板的介面顯示結果（`Ctrl+F`）。服務先在記憶體中比對名稱，再以呼叫者的身分開啟每個結果所在的資料夾，
能列出（且磁碟區序號與記錄編號相同）才回傳；同一次搜尋中每個資料夾只檢查一次。

**原因**：
- 索引服務已經讀取 MFT、跟著變更日誌更新，加上名稱就是 Everything 的做法，搜尋不必碰磁碟：100 萬個名稱約 10 ms。
- 服務以 LocalSystem 執行，看得到所有檔名；以呼叫者身分過濾後，結果等同使用者自己能列舉到的，不會洩漏別人資料夾裡的名稱。
  只回報找到的數量與「還有更多」，不回報未過濾的總數。
- 用命令面板的外觀與按鍵：不必修改清單模型（清單的項目都在同一個資料夾），Enter 前往所在位置正好接上一般的瀏覽。

**代價與處理**：
- 服務的記憶體增加：每 100 萬筆記錄由約 20 MB 增加到約 45 MB。名稱以兩位元組長度加 UTF-8 存放，
  改名留下的空間超過 16 MB 且超過一半時整理。
- 大小寫只有 ASCII 字母不分（逐位元組比對才快）；其他語言的大寫字母（如 É）要打一樣的字。
- 沒有索引（服務未安裝、非 NTFS、網路磁碟）時不能搜尋，面板顯示如何啟用。舊版服務回「無法解析請求」時提示更新。
- 每次最多 500 個結果、3 秒：常見的詞會有很多結果，以「500+ 個」表示還有更多，請再加詞縮小範圍。

## 2026-10-15　樹狀列：監看展開中的節點

**代價**：超過 63 個展開的節點時，後面的不監看（點擊展開時仍會在背景重新確認）；監看中的資料夾會被開啟一個控制代碼。

## 2026-10-15　`run` 預設不顯示主控台視窗

**決定**：`run`（設定檔、命令面板、Lua）執行主控台程式（PE 子系統為主控台、DOS 程式、`.bat`、`.cmd`）時以 CREATE_NO_WINDOW
直接建立程序；視窗程式、文件、網址、App Paths 登錄的名稱仍交給 ShellExecuteEx。要顯示主控台時加 `--console`（Lua 為 `console = true`）。
Lua 的 `os.execute`、`io.popen` 換成不顯示主控台視窗的版本。開啟檔案（按兩下、`open`）與網址列輸入維持檔案總管的行為。

**原因**：zing 是視窗程式，沒有主控台；每執行一個主控台程式（例如批次解壓縮時的 tar）就會閃出一個主控台視窗。
腳本與按鈕執行的多半是批次工具，需要互動的終端機是少數，所以預設隱藏、少數情況明確指定。

**代價與處理**：
- 不能一律隱藏：以 SW_HIDE 啟動會連視窗程式本身也藏起來，所以先判斷程式類型（`SHGetFileInfoW` 的 SHGFI_EXETYPE）。
- 互動式主控台程式（`cmd`、`pwsh`、`python`）若沒加 `--console` 會在背景執行、看不到；預設設定只有 `run wt.exe`（視窗程式），不受影響。
- 找程式的順序是 System32、PATH（依 PATHEXT 補副檔名），與 CreateProcess 的搜尋順序不完全相同；找不到的交給 ShellExecuteEx。
- `io.popen` 的讀取模式等命令結束後一次取得全部輸出，不是串流；寫入模式沿用標準版本（會閃視窗）。

## 2026-10-14　Lua 腳本：Lua 5.4（mlua 內建）、函數式但不用 functor／monad、release 維持 panic = "abort"

**決定**：
- 用 `mlua` 0.11 搭配內建編譯的 Lua 5.4（`vendored`），開放完整的標準函式庫；腳本在專用執行緒執行，命令 30 秒、縮圖規則 0.3 秒的 CPU 時間上限
  （以腳本執行緒的 CPU 時間計算：等待 `ask()`、外部程式、檔案 I/O 不計，批次解壓縮這類長時間但多半在等待的腳本不會被誤殺）。
- prelude 提供惰性求值（`seq`）、不可變（`freeze`）、組合（`compose`／`pipe`／`partial`、`|` 管線），但不提供 functor／monad。
- release 維持 `panic = "abort"`，改由程式規則保證 Lua 的錯誤不穿過 Rust 的堆疊框架。

**原因**：
- 執行檔增加約 0.79 MB（2.60 → 3.39 MB），建置時間多約 40 秒；LuaJIT 或外部 DLL 都會讓可攜式的單一執行檔變複雜。
- 10 萬筆資料實測：迴圈 8 ms、map/filter/reduce 11 ms、惰性串流 12 ms、Maybe monad 65 ms。前三者差距小，monad 慢 5–8 倍，
  而且在 Lua 裡寫起來不自然，所以只保留函數式設計中成本低的部分。
- Windows 上 Lua 的錯誤是用 SEH 展開的 longjmp；`panic = "abort"` 時 Rust 函式都標為不可展開，錯誤只要穿過 Rust 框架
  （例如 mlua 的 `set_hook` 回傳錯誤、Rust 函式的參數型別不符）程序就會直接結束（release 冒煙測試實際發生過，0xC0000409）。
  改成 `panic = "unwind"` 可以根治，但執行檔再多 0.86 MB（+25%）。

**代價與處理**：
- Rust 提供給 Lua 的函式參數一律收 `Value`、不回傳 `Err`；時間上限用 prelude 裡的 Lua 鉤子（`debug.sethook`，並包裝
  `coroutine.create`／`wrap` 讓協程也受限制）；Rust 端讀寫全域變數只用 `raw_get`／`raw_set`。
- 冒煙測試涵蓋：錯誤、無窮迴圈、協程裡的無窮迴圈、型別錯誤的參數、全域表設了會報錯的 metatable，並以 release 執行。
- 規則由工具把關（2026-10-15 補上）：`clippy.toml` 禁止 `create_function`、`set_hook`、會觸發 metamethod 的 `Table` 方法，
  Rust 函式一律經 `script::lua_fn`（參數型別以 `SafeArgs` 限制為 `Value` 組合）；冒煙測試的 debug build 改用
  `panic = "abort"` 的 `debug-abort` profile，實測放入違規後 debug 冒煙測試即以 0xC0000409 結束。
- 腳本可以自己呼叫 `debug.sethook` 拿掉時間上限；腳本與設定檔同等可信，不另外防範。

## 2026-10-14　預覽處理常式以「沒有擁有者」的頂層視窗承載

**決定**：Windows 預覽處理常式（IPreviewHandler）在專用的 STA 執行緒上，用一個沒有父視窗、也沒有擁有者的
頂層彈出視窗（WS_POPUP、WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW）承載，疊在預覽窗格的內容區。

**原因**：第三方處理常式可能卡住。跨執行緒的父子視窗**或擁有者／被擁有視窗**都會讓系統連結兩個執行緒的輸入佇列，
處理常式的執行緒卡住時會連帶卡住 UI（原本以為擁有者視窗可以避免，查證後不行）。獨立的頂層視窗不會連結。

**代價與處理**：
- 視窗的 Z 順序要自己維護：主視窗啟用時以 SWP_ASYNCWINDOWPOS 把它放回上層；命令面板、批次重新命名面板開啟或視窗最小化時暫時隱藏。
- UI 只用不會等待的方式操作它（PostThreadMessage 傳請求、SWP_ASYNCWINDOWPOS、ShowWindowAsync）。
- 看門狗 3 秒：逾時就放棄該執行緒（之後換新的），改顯示縮圖；被放棄的執行緒恢復後自行關閉視窗並結束。
- 優先以 CLSCTX_LOCAL_SERVER 建立（prevhost.exe），處理常式當掉不影響本程式。
- 冒煙測試的截圖（PrintWindow）不含這個視窗。

## 2026-10-14　批次重新命名改用完整的 `regex`

**決定**：批次重新命名的規則運算式使用 `regex`（預設功能），不用 `regex-lite`。

**原因**：`regex-lite` 不支援 Unicode 感知的比對，對中文檔名影響明顯（實測）：

| 寫法 | `regex-lite` | `regex` |
| --- | --- | --- |
| `\w` 比對「中」 | 不符合（只認 ASCII） | 符合 |
| `\d` 比對全形「３」 | 不符合 | 符合 |
| `\s` 比對全形空白 | 不符合 | 符合 |
| `(?i)` 讓 ä 等於 Ä | 不符合（只對英文字母） | 符合 |
| `\p{Han}` 等 Unicode 類別 | 不支援 | 支援 |

兩者都不支援後向參照與環視；其他語法（群組、`$1`、`${名稱}`、量詞、錨點）相同。

**代價**：執行檔增加約 1.1 MB（實測：`regex-lite` 約 52 KB；`regex` 只開 `unicode-perl`、`unicode-case` 多 881 KB；
預設功能多 1,118 KB），由 1.505 MB 變為 2.597 MB，仍在 10 MB 門檻內；`perf/baseline.json` 的 `exe_mb` 隨之更新。
只有使用批次重新命名的規則運算式時才會用到，啟動時間不受影響（53 ms，在容差內）。

**考慮過的替代方案**：維持 `regex-lite` 並在面板提示改寫法（中文用 `[一-鿿]`、全形數字用 `[0-9０-９]`），
或 `regex` 只開部分 Unicode 功能；使用者選擇完整的 `regex`。
